# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет `S12-hw-dataset.csv`, прогнозировалась колонка `target` на шаг вперёд (`horizon=1`).
- Выполнен корректный `train / validation / test` split по времени без перемешивания.
- Сравнены подходы `B1` (naive-last), `B2` (moving-average), `B3` (ridge по лаговым/rolling признакам), `R1` (GRU).
- Лучший подход выбран по `validation MAE`: **R1**.

## 2. Среда и воспроизводимость

- Python: 3.x
- pandas / numpy / scikit-learn: актуальные версии из окружения
- torch: 2.7.1+cu118
- Устройство (CPU/GPU): cuda
- Seed: 42
- Как запустить: открыть `HW12.ipynb` и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: почасовая
- Горизонт прогноза: 1 шаг
- Размер датасета: 4320
- Диапазон дат: 2025-01-01 00:00:00 — 2025-06-29 23:00:00
- Есть ли дополнительные внешние признаки: нет (только `date`, `target`)
- Комментарий (2-4 предложения): ряд демонстрирует выраженную внутрисуточную сезонность и шум. Есть участки локального тренда, что требует аккуратной валидации по времени. Пропусков в исходных колонках нет, но при генерации лагов и rolling появляются `NaN` в начале ряда, они удаляются до обучения.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: хронологически, без shuffle.
- Какие доли или интервалы использовались: 70% / 15% / 15%.
- Почему `random split` здесь некорректен: он смешивает прошлое и будущее, создавая утечку и завышенную оценку качества.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7` (по `target.shift(1)`)
- Какие календарные признаки использовались: `day_of_week`, `hour`
- Как обрабатывались пропуски после построения лагов/rolling: удалены строки с `NaN` в начале ряда
- Использовалось ли масштабирование и где именно оно обучалось: да, `StandardScaler` обучался только на train (для `B3` по X, для `R1` по target)

## 7. Анализ

Наивный baseline часто служит сильной нижней границей для инерционных рядов, но обычно проигрывает, когда присутствует выраженная сезонность. Moving average сглаживает шум, но может запаздывать на резких изменениях и поэтому не всегда даёт лучший MAE. Лаговые и rolling-признаки позволяют линейной модели учитывать краткосрочную динамику и периодику, что часто улучшает качество относительно B1/B2. Ridge даёт устойчивость за счёт регуляризации и уменьшает переобучение на коррелированных признаках. GRU полезна, когда в последовательности есть нелинейные зависимости и паттерны, которые трудно выразить фиксированным набором признаков. При этом на коротких и относительно простых рядах выгода от нейросети может быть умеренной при большей вычислительной стоимости. Основные риски утечки данных в таких задачах: вычисление rolling/lag без `shift`, обучение scaler на полном датасете, подбор гиперпараметров по test. Выбор лучшей модели по validation принципиален, потому что test должен оставаться независимой оценкой обобщающей способности. Характерные ошибки обычно возникают в точках локальных переломов тренда и на экстремумах сезонной волны.

## 8. Итоговый вывод

В качестве базового решения для подобной задачи разумно начать с модели на признаках (`Ridge` + лаги/rolling), так как это дешево и интерпретируемо. Если ряд демонстрирует выраженную нелинейность и сложные зависимости, имеет смысл переходить к `GRU`. Простых baseline может быть достаточно для быстрых проверок и мониторинга деградации качества. Ключевой вывод: для временных рядов корректная temporal-валидация важнее, чем формально более низкая метрика, полученная с некорректным random split.
